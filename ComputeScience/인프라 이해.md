# 개발/보안/인프라 이해

## IT 구조의 핵심 개념 이해

### IT 시스템 구성요소 및 동작원리

- Client
  - 클라이언트는 자체적으로 비즈니스 로직을 판단하진 않음
  - 입력을 모으고, 결과를 표시하는데 집중
    - 최소한의 입력값 검증
  - 금융권에서 클라이언트가 중요한이유: **보안**
    - 키보드 보안(키로깅 방지)
    - 백신 연동
    - 공인인증서 및 전자서명 수단 설치 요구
  - PC나 단말 자체가 해킹되어 있을 가능성을 가정
    - 입력 단계에서부터 정보 유출과 위변조를 막기 위한 다층적 방어 체계
- Network
  - 방화벽
    - 허용 IP와 포트만 통과
  - 로드밸런서
    - 트래픽 분산
    - 부하 방지 및 장애 시 가용성 확보
      - 무중단 운영을 가능
  - 망 분리
    - 물리적 or 논리적
      - 여러 겹의 방어선을 두기 위함
      - 3단 분리
        - 인터넷망 / 금융망 / 내부망
- Server
  - 비즈니스 로직 처리 및 DB 상호작용
  - Web Server
    - 정적 콘텐츠
  - WAS
    - 비즈니스 로직 등의 동적 처리
  - AP Server
    - 정기적 *배치* 작업 수행
  - 분리를 통한 안정성 확보 및 장애 전파 차단
- DB
  - SW적 개념
  - 금융권에서는 주로 RDBMS 사용
    - For *트랜잭션 무결성* (ACID)
- Storage
  - DB의 데이터, 문서, 이미지, 로그, 파일 등이 실제 저장되는 *물리적 공간(HW)*
  - SAN (Storage Area Network)
    - 서버와 직접 연결
    - 빠른 I/O 제공
  - NAS (Network Attached Storage)
    - 네트워크 공유 파일 저장
    - 공유 폴더 느낌
  - 백업 Storage
    - 데이터 복사본 이중화
    - DR 대비

| 구분 | SAN | NAS |
| --- | --- | --- |
| 접근단위| 블록 | 파일 |
| 속도 | 빠름 | 상대적 느림 |
| 주 용도 | DB, 트랜잭션 처리 | 파일 공유, 아카이브 |
| 사례 | 계정계 DB, 승인계 | 로그, 문서, 녹취 등 |

### 채널계 / 계정계 구조 이해 및 금융시스템 구성요소
- 각 영역이 분리된 책임을 가짐
  - 장애 전파 차단 및 가용성 확보
- 채널계
  - 고객 접점 통로
    - 인터넷뱅킹, 앱, ATM, 창구, ARS, 오픈 API 등
    - 사용자 인증 -> 입력값 검증
    - 채널마다 허용 업무 범위 다른 것 주의
      - *채널마다 가진 보안 수준과 본인확인 강도가 다름*
    - 예시
      - 앱에서 이체 시, 앱은 WAS를 통해 인증 토큰(JWT / Session)을 검증, 이체 요청을 계정계로 전달
      - 이체 금액이 일정 금액 이상이면 OTP나 생체인증 등 추가 인증 진행
      - FDS 연계
        - 시간대 / 기기 / IP 발생 거래 확인 및 위험도에 따른 거래 보류
      - 입력값 검증
        - 출금 가능 여부 조회 등의 비즈니스 로직 검증은 계정꼐에서 진행
      - 채널계 -> 계정계 or 대외계 (타행 이체 시) 등으로 연결
- 계정계 (코어뱅킹)
  - 원장
    - 법적으로 보관할 의무가 있는 거래의 공식 기록
    - ACID
      - Atomicity (원자성) / Consitency (일관성) / Isolation (격리성) / Duration (지속성)
    - EOD (End of day, 일일 마감)
      - 이자 계산 및 각종 결산 처리 진행
- 정보계
  - 데이터웨어하우스(DW) 구축 및 운영
  - 기처리된 데이터 바탕, 의미 있는 정보 추출
    - KPI 보고서, 고객 세그먼트 분류, 마케팅 활용 CRM, 리스크 관리 및 자금 운용 계획 등
  - 정보계 / 계정계 망 분리
    - 실시간 거래 처리 성능에 영향을 주지 않기 위함
  - 예시
    - ETL (Extract - Transform - Load) 프로세스를 통한 정보계 DW 이관
      - 이후 금감원 제출용 규제 보고서 생성
      - 고객별 신용점수 재산정 및 여신 한도 재계산
      - 마케팅 부서의 고객 세그먼트 분석
  - 실시간성 보다 정확성 및 대용량 처리 최적화
    - RDBMS보다는 컬럼 지향 저장 / OLAP 큐브 등 사용
- 대외계
  - 외부 기관과 데이터 송수신
  - 예시
    - 금결원 타행이체 공동망 / 지로 / CMS(자금관리서비스)
    - 한국은행 BOK-Wire
      - 대금융기관 간 거액 자금 결제
    - 금감원 / 금융위
      - 정기적 감독보고 및 규제 데이터 제출
      - FDS 및 자금세탁방지 데이터 포함

### 웹서비스 구조: Browser -> Web Server -> WAS -> DB
- Browser (클라이언트)
  - 사용자가 가장 먼저 마주하는 화면, 웹 거래의 시작점
  - 기존 ActiveX (플러그인) 사용
    - 브라우저 표준으로 부족한 보안을 보충하기 위해
    - 단점
      - 특정 브라우저에서만 동작
      - 보안 취약점 관리가 어려움
  - 현재 HTML5 기반으로 전환
    - 브라우저 및 운영체제 호환성 확보
  - 모바일
    - 주로 네이티브 앱 사용
      - OS 차원 보안 기능 직접 활용 가능
  - 처리 흐름
    - 버튼 클릭 -> 브라우저는 정적 자원 렌더링 및 클라이언트 단 유효성 검증 -> 요청은 HTTPS(TLS 1.2 이상)로 암호화되어 전송
- Web Server
  - 정적 파일 제공
  - HTTPS 통신 암복호화 담당
    - 주로 443 port 
  - 동적 요청 WAS 바이패스
    - *리버스 프록시*
      - EX) Apache, Nginx 등
      - 보통 클라이언트의 기능을 대체하면 프록시, 서버의 기능을 대체하면 리버스 프록시로 통칭함
  - 처리 흐름
    - 웹 서버 요청 수신 -> 정적 리소스 처리 및 응답 -> 동적 요청 WAS 전달 (리버스 프록시)
    - Web Server는 DMZ에 위치
      - 1차 방화벽 통과한 트래픽만 도달
    - SSL 종단을 처리, 암호화 부담을 분산
      - Web Server 이후에는 Http로 진행
- WAS
  - 비즈니스 로직 실행
  - DB Connection pool
    - DB와의 연결을 미리 만들어두고, 꺼내 쓰고 반납
      - EX) 채널계는 주간 시간대에 짧고 빈번한 조회성 트랜잭션
      - EX) 야간 AP Server 배치는 소수 커넥션으로 대용량 데이터 장시간 처리
      - 주로 배치용 / 온라인용 풀 물리적 분리
        - 동일 풀 공유시, 배치 작업이 커넥션을 오래 점유해 온라인 채널의 응답성을 저해함
  - 세션 관리
    - HTTP는 매번 독립적 요청으로 처리
    - 세션을 통해 로그인 및 거래 진행 상태 유지
  - 트랜잭션 관리
    - 오류 발생 시 롤백
  - 계층별 처리 흐름
    - 셰션/토큰 검증을 통한 사용자 인증
    - 잔액 조회 및 이체한도 검증
    - FDS 연동
    - 트랜잭션 시작
    - 대외계 연동
    - 커밋 or 롤백
  - 주로 2차 방화벽 안쪽 내부망에 위치, 외부에서 직접 접근 불가능
- DB
  - ACID 트랜잭션
  - All or Nothing (Atomicity)
  - 격리수준 Read Committed 이상
    - Non-Repeatable Read / Phantom Read 등은 방지 어려움

## 서버 및 네트워크 기초
### Linux (서버) 기본 구조
- Linux 구조
  - Hardware, Kernel, Shell, Application
  - Hardware
    - CPU, 메모리, 디스크, 네트워크 카드와 같은 물리적 자원
  - Kernel
    - Linux OS의 핵심, HW와 SW 사이에서 자원 관리
    - CPU 스케줄링, 메모리 할당, 파일시스템 관리, 네트워크 관리, 디바이스 드라이버 등
    - 커널은 HW를 SW가 쉽게 사용할 수 있는 형태로 추상화
  - Shell
    - 명령어를 System Call로 변환하는 역할
    - bash, sh, zsh 등
      - 금융권에서는 bash가 표준
    - 자동화 스크립트, 배치작업, 시스템 운영 대부분이 bash 기반 작성
  - Application
    - WAS, DB, 모니터링 도구 등
- 디렉터리
  - Linux는 모든 것을 파일로 표현
  - `/etc`
    - 시스템 전체와 각 애플리케이션의 설정 파일
    - `/etc/hosts`
      -  도메인 이름, IP주소 대응관계를 수동 정의
    -  `/etc/passwd`
      -  시스템 등록 사용자 계정 정보
    - 해당 디렉터리 파일 추적이 변경관리의 핵심 대상
  - `/var/log`
    - 로그 파일 저장
    - 시스템 로그, WAS 로그, DB 로그 등
  - `/proc`
    - 디스크에 실제 저장된 파일 아님
    - 커널이 현재 실행 중 프로세스와 시스템 상태 정보를 파일처럼 보이도록 메모리 위에 만들어두는 가상 파일시스템
    - `/proc/cpuinfo`
      - 현재 CPU 상세 정보 확인
    - `/proc/meminfo`
      - 메모리 사용 현황 실시간 조회
    - 운영자나 모니토링 도구가 시스템 상태 실시간 파악 시 해당 디렉터리 활용
  - `/home`
    - 사용자 계정에 배정된 개인 작업 공간
    - `/home/googoo9918`
      - 사용자 개인 디렉터리
- Linux 운영 관점 
  - root 직접 사용 지양
  - 변경관리
    - 변경 시 사전 문서화 & 관계자 승인 및 원본 파일 백업
  - Linux는 시스템 효율 및 미세 조정의 유연성 제공
    - 오픈소스 기반으로, 특정 벤더에 종속되지 않음
- 실무 구성 예시
  - 대충 눈에 익히기만 하자
  - 계정계 서버

      - 이중화 및 DR 미러링
    - 배치 서버

    - DW/DM 서버
      - Teradata, Oracle Exadata등 대용량 분석 특화 어플라이언스 장비
    - ETL 서버
    - FDS 서버
      - Kafka 등의 메세지 큐
### CPU, Memory, Disk

- CPU(Central Processing Unit, 중앙처리장치)
  - 서버의 모든 계산과 논리 판단을 실제 처리
  - Core
    - CPU의 독립적 연산 단위
    - 병렬 처리 가능
  - 사용률(Utilization)
    - 사용률이 높으면 응답 지연 -> 장애 전조 신호
  - `top`
    - 현재 실행 프로세스 및 각 프로세스 소비 CPU 및 메모리 자원 노출
  - `vmstat`
    - CPU 사용률, 메모리 상태, 디스크 I/O, 프로세스 대기 상태 등 전반의 자원 현황 주기적 출력
- Memory(RAM, Random Access Memory)
  - 휘발성
    - 서버 재시작시 초기화
  - Swap
    - 메모리 부족 시 발생
    - 메모리 공간 부족 시, 디스크 일부 영역을 메모리처럼 사용
      - 디스크와의 속도차이로 인하여 Swap 활성화 순간 서버 응답 속도 하락
      - 응답 지연 및 타임아웃 오류 등 장애 주요 원인
  - JVM Heap 메모리
    - Java WAS 시작 시 메모리 영역(Heap) 크기를 미리 설정받아 모든 작업을 처리
    - Heap크기가 너무 작을 시 Out Of Memory 발생
    - 크게 설정 시 타 프로세스 사용 메모리 줄어듦
  - Memory Leak
    - 사용 메모리 미반환 시, Heap 한계 도달
    - 메모리 누수 모니터링 중요
- Disk
  - 비휘발성
  - HDD(Hard Disk Drive)
    - 대용량 비교적 저렴하게 구성
    - 기계적 움직임 수반, 속도가 느리고 물리적 충격에 취약함
  - SSD
    - 반도체 기반으로 동작, 기계적 움직임 X
    - HDD에 비해 데이터 접근 속도 빠름
  - RAID(Redundant Array of Independent Disks)
    - 여러 개의 디스크를 하나의 논리적 단위로 묶어 안정성을 높임
    - RAID 0
      - 한 디스크 고장 시, 전체 데이터를 잃는 위험 존재
      - 성능이 중요하고 데이터 손실 감수할 수 있을 시 제한적 사용
    - RAID 1
      - 두 디스크에 동일 데이터 복사, 미러링
    - RAID 5
      - 데이터와 패리티 정보를 분산 저장
      - 하나의 디스크 장애를 견딜 수 있도록 하면서 저장 공간 효율을 챙김
    - RAID 10
      - RAID1의 미러링과 RAID 0의 분산 결합
      - 속도와 안정성 동시 확보
      - 금융 핵심 시스템은 주로 RAID 10에 더해 실시간 백업 병행
- 실무 예시
  - FDS
    - CPU 코어 수 기준 Auto Scaling
      - 임계치 넘으면 자동 인스턴스 증설
  - WAS Heap Memory 관리
    - 세션 객체 급증 시, Full GC(Garbage Collection) 발생 -> 응답 지연(latency 증가)
    - 힙 메모리 크기를 사전에 할당, GC 로그 분석 -> 튜닝 필수적
  - DB Buffer Pool
    - 자주 조회되는 데이터는 메모리 상 버퍼 풀에 캐싱
    - 버퍼 풀 Hit Ratio 95% 이상 유지되도록 설계
      - 디스크 I/O 증가 유의
  - Memory Leak 장애 사례
    - 객체 미해제 시 OOM 주의
  - Transaction log 저장
    - 모든 금융거래는 5년 이상 로그를 디스크에 기록해야하는 의무 존재
    - 오래된 로그 자동 아카이빙 or 별도 스토리지(NAS) 이관
  - SAN/NAS 스토리지 이중화
    - 장애 발생 시 즉시 전환(Failover), HA(High Availability, 고가용성) 구성 핵심 요소
  - I/O 성능 저하
    - 배치 mass Write와 실시간 read가 같은 스토리지 공유 시, I/O 경합(Contention) 발생
    - 이를 방지하기 위해 스토리지 티어링(Tiering), QoS(Quality of Service)설정 적용
### 프로세스 및 로그의 이해
- 프로세스
  - 프로그램 != 프로세스
    - 프로그램은 정적 실행 파일
    - 프로세스는 프로그램이 메모리에 올라가 실행되는 상태
  - 프로세스 생애주기
    - Created -> Ready (CPU 배정 대기) -> Running (CPU 점유) -> Terminated
    - Waiting
      - I/O 작업 및 네트워크 응답 완료 대기
      - CPU 미점유
        - 해당 시간을 다른 Ready 상태 프로세스에게 배정
        - 이를 통해 프로세스가 마치 동시에 실행되는 것처럼 보이는 멀티태스킹이 가능함
    - 좀비 프로세스
      - 생애주기가 정상적으로 마무리되지 않은 상태
      - 부모 프로세스가 회수 작업을 수행하지 않음
      - 누적 시 새 프로세스 생성 불가
  - 관리 명령어
    - `ps -ef`
      - 모든 프로세스 목록 출력
      - PID, 부모 프로세스 번호, 실행 시각, 명령어 등
    - `top`, `htop`
      - 프로세스 현황
      - CPU / 메모리 소비량 등
      - htop은 top 시각적 개선 버전
    - `kill -9 [pid]`
      - 강제 종료
- 로그
  - 시스템 로그
    - OS, Kernel, HW 발생 이벤트 기록
    - `/var/log/messages`에 주로 저장
      - 서버 부팅, 하드웨어 이상, 커널 경고 메시지 등
  - 애플리케이션 로그
    - WAS, DB 배치 프로그램 등 업무 처리 로그
    - 오류 메시지, Stack Trace 등
  - 보안 및 감사 로그
    - 서버 접속, 거래 실행자 등 기록
  - 금융권 로그 관리 특징
    - 로그의 위변조 방지
      - 별도 로그 서버 저장
      - 삭제 및 수정 불가능 정책 등
    - 통합 로그 관리 체계 운영
      - ELK(Elasticsearch, Logstash, Kibana 등), Splunk 등의 통합 로그 관리 플랫폼
      - FDS와도 연계
    - 로그의 타임스탬프
      - 로그 시간 순서 정렬 -> 어느 서버에서 무슨 오류가 처음 발생했는지 역추적(Root Cause Analysis)
      - 서버 시간 동기화 필수
        - NTP(Network Time Protocol) 시간 동기화 프로토콜
    - 프로세스와 로그의 관계
      - 결국 로그는 특정 프로세스가 남긴 것
      - 프로세스의 상태와 함께 볼 수 있어야 함
### TCP/IP
- TCP/IP 4계층
  - 응용 계층
    - HTTP, HTTPS, FTP, SMTP, DNS, SSH 등
  - 전송계층
    - TCP 
      - 연결 / 수신 확인 / 재전송 등
      - 속도보다 정확성 및 신뢰성 우선
    - UDP
      - 비연결 / 즉시 전송 / 도착 여부 확인 X
      - 빠르고 처리 부담 적음
    - 포트번호를 통해 프로세스 구분
  - 인터넷 계층
    - IP를 통해 출발지 / 목적지 식별
    - 라우터를 통해 라우팅 경로 설정
      - 손실 보장은 TCP가 담당
  - 네트워크 접근 계층
    - 물리적 매체를 통해 전기 신호 / 광신호 형태로 전송
    - 이더넷 케이블, 무선 와이파이, 광케이블 등
    - MAC 주소
  - 캡슐화
    - Data -> TCP Header(출발/도착 포트) -> IP Header(출발/도착 IP주소) -> Ethernet(MAC 주소)
    - 역캡슐화는 역순
  - TCP 3-Way Handshake
    - SYN
      - 클라이언트가 서버에 연결 요청 신호
      - 순서 추적을 위한 순서 번호 포함
    - SYN-ACK
      - 요청을 받았다는 확인(ACK)
      - 서버가 클라이언트에게 연결을 요청하는 SYN 신호를 함께 보냄
      - 클라이언트가 보낸 순서 번호를 인식 & 자신의 초기 순서 번호도 함께 전달
    - ACK
      - 서버 연결 요청에 대한 확인 신호를 보냄
    - 순서 보장
      - 패킷 손실 시 재전송 요청
    - 통신 종료 시 4-Way Handshake
    - 네트워크 장애 분석 시 `netstat, tcpdum`등으로 패킷 흐름 확인
### 포트 및 프로토콜
- 포트를 통해 서버 내 서비스 구분
- IP 주소 + 포트 번호의 결합을 소켓이라 함
- 포트 번호
  - 0~1023
    - Well-known poert
    - EX) HTTP: 80 / HTTPS: 443 / SSH: 22 / FTP: 21 / SMTP: 25
    - OS 차원에서 관리, 포트 관리를 위해서는 관리자 권한 필요
  - 1024 ~ 49151
    - Registered Port
    - 애플리케이션 / 서비스 제공업체가 IANA(Internet Assigned Numbers Authority) 기관에 등록해 사용하는 포트 범위
    - EX) ORACLE: 1521 / MySQL: 3306 / SQL Server: 1433
  - 49152 ~ 65535
    - Dynamic Port (Private Port)
      - 클라이언트가 서버에 연결 시도 시, OS가 임시로 자동 배정
      - 브라우저가 해당 범위 내에서 임의의 포트 번호를 통해 출발지 포트로 사용
        - 통신 종료 시 임시 포트 반환
- 금융권 포트 관리
  - Deny All, Allow Exception
  - 모든 포트 차단, 업무상 필요한 포트만 허용
- 프로토콜 선택
  - Telnet(23 Port)
    - 통신 내용이 암호화되지 않은 평문
  - SSH(22 Port)
    - 접속 시 교환되는 모든 데이터를 암호화
- 포트 스캔
  - 현재 어떤 포트가 열려 있는지를 주기적으로 점검
  - 모든 포트에 순서대로 접속을 시도, 열려 있는 포트를 목록으로 만들어 냄
  - 비인가 개방 포트 점검
### 방화벽, VPN, NAT
- 방화벽 
  - Default Deny, Default Allow 가능
  - 1차 방화벽
    - 외부 인터넷과 DMZ 사이 위치
  - 2차 방화벽
    - DMZ와 내부 금융망 사이 위치
  - 초기 방화벽
    - IP 주소와 포트번호만 보고 판단
    - 이후 연결 상태 추적
    - 최근 패킷 내용까지 분석
- VPN (Virtual Private Network)
  - 공공 인터넷망을 통해 통신, 전용 회선처럼 안전하게 데이터를 주고받을 수 잇도록 암호화된 터널을 만듦
  - 터널링/암호화
    - 전송 전 암호화, 패킷으로 패킹해서 전송
  - IPSec VPN
    - 네트워크 계층에서 동작
    - 두 네트워크 사이 모든 트래픽을 암호화
      - Site-to-Site VPN에 주로 사용
  - SSL VPN
    - 애플리케이션 계층에서 동작
    - 브라우저나 별도 클라이언트 프로그램을 통해 개별 사용자가 내부망 접속 시 사용
    - EX) 재택근무
  - MPLS(Multi-Protocol Label Switching)
    - 완전 분리된 물리적 망
    - 공공 인터넷망을 전혀 거치지 않고, 외부 침입 가능성이 원천적으로 배제
- NAT (Network Address Translation)
  - 네트워크 패킷에 포함된 IP주소를 다른 IP주소로 변환
    - EX) 사설 IP 주소를 외부 통신 시 공인 IP 주소로 변환
  - 공인 IP 주소의 부족 문제
    - 43억개 존재
    - NAT 사용 시 내부 수백대 서버 각각 사설 IP를 통한 내부 통신
      - 외부 통신 필요 시에만 공인 IP를 공유해 사용 
    - 사설 IP 대역
      - 인터넷에서는 라우팅되지 않고, 내부망 전용으로만 사용
      - `10.0.0.0 ~ 10.255.255.255`
      - `172.16.0.0 ~ 172.31.255.255`
      - `192.168.0.0 ~ 192.168.255.255`
  - 내부 구조의 은닉
    - 외부에서 바라보면, 모든 서버가 소수의 공인 IP 주소로만 보임
    - 내부 서버가 각각 어떤 사설 IP를 사용하는지는 외부에서 알 수 없음
- 실무 예시
  - 외부 구간 ~ DMZ
    - 1차 방화벽, HTTPs(443)만 허용
  - DMZ ~ 내부망(채널계)
    - 2차 방화벽, 웹서버 To 채널계 서버로의 특정 포트만 화이트리스트로 허용
  - 내부망(채널계) ~ 계정계
    - 3차 방화벽 or 망분리 스위치
  - 재택근무/원격 유지보수용 VPN
    - SSL VPN 사용 및 OTP/FIDO 등 MFA 적용
    - 접속 가능 시단개, 접속가능 IP, 세션 타임아웃 설정 등
  - Site-to-Site VPN 예시
    - 전산센터 to DR / 계열사 간 연계 시 IPsec VPN 터널 구성
  - 클라우드 전환 시 하이브리드 VPN
    - AWS/Azure 등 VPC와 온프레미스 데이터센터 연결 시
      - VPN Gateway + Customer Gateway 구성
  - Static NAT (1:1 NAT)
    - 외부 서비스 오픈 시
    - 인터넷뱅킹 웹서버를 외부에 서비스하기 위해 고정 공인 IP로 1:1 매핑
    - 대외기관 통신 시 방화벽 정책과 결합, 화이트리스트 등록
  - Dynamic NAT / PAT (NAT Overload)
    - 내부 사용자 외부 접속
    - 내부 직원 PC가 외부 인터넷에 접속 시, 소수 공인 IP를 다수 내부 IP가 공유 (PAT)
  - 대외계 연결 시 NAT 활용
    - 상대 기관에는 실제 내부 IP가 아닌 NAT된 IP만 노출
    - EX) 내부 사설 서브넷 서버 대외기관 통신 시 NAT Gateway를 통해 클라우드 공인 IP로 변환 후통신
