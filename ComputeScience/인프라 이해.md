# 개발/보안/인프라 이해

## IT 구조의 핵심 개념 이해

### IT 시스템 구성요소 및 동작원리

- Client
  - 클라이언트는 자체적으로 비즈니스 로직을 판단하진 않음
  - 입력을 모으고, 결과를 표시하는데 집중
    - 최소한의 입력값 검증
  - 금융권에서 클라이언트가 중요한이유: **보안**
    - 키보드 보안(키로깅 방지)
    - 백신 연동
    - 공인인증서 및 전자서명 수단 설치 요구
  - PC나 단말 자체가 해킹되어 있을 가능성을 가정
    - 입력 단계에서부터 정보 유출과 위변조를 막기 위한 다층적 방어 체계
- Network
  - 방화벽
    - 허용 IP와 포트만 통과
  - 로드밸런서
    - 트래픽 분산
    - 부하 방지 및 장애 시 가용성 확보
      - 무중단 운영을 가능
  - 망 분리
    - 물리적 or 논리적
      - 여러 겹의 방어선을 두기 위함
      - 3단 분리
        - 인터넷망 / 금융망 / 내부망
- Server
  - 비즈니스 로직 처리 및 DB 상호작용
  - Web Server
    - 정적 콘텐츠
  - WAS
    - 비즈니스 로직 등의 동적 처리
  - AP Server
    - 정기적 *배치* 작업 수행
  - 분리를 통한 안정성 확보 및 장애 전파 차단
- DB
  - SW적 개념
  - 금융권에서는 주로 RDBMS 사용
    - For *트랜잭션 무결성* (ACID)
- Storage
  - DB의 데이터, 문서, 이미지, 로그, 파일 등이 실제 저장되는 *물리적 공간(HW)*
  - SAN (Storage Area Network)
    - 서버와 직접 연결
    - 빠른 I/O 제공
  - NAS (Network Attached Storage)
    - 네트워크 공유 파일 저장
    - 공유 폴더 느낌
  - 백업 Storage
    - 데이터 복사본 이중화
    - DR 대비

| 구분 | SAN | NAS |
| --- | --- | --- |
| 접근단위| 블록 | 파일 |
| 속도 | 빠름 | 상대적 느림 |
| 주 용도 | DB, 트랜잭션 처리 | 파일 공유, 아카이브 |
| 사례 | 계정계 DB, 승인계 | 로그, 문서, 녹취 등 |

### 채널계 / 계정계 구조 이해 및 금융시스템 구성요소
- 각 영역이 분리된 책임을 가짐
  - 장애 전파 차단 및 가용성 확보
- 채널계
  - 고객 접점 통로
    - 인터넷뱅킹, 앱, ATM, 창구, ARS, 오픈 API 등
    - 사용자 인증 -> 입력값 검증
    - 채널마다 허용 업무 범위 다른 것 주의
      - *채널마다 가진 보안 수준과 본인확인 강도가 다름*
    - 예시
      - 앱에서 이체 시, 앱은 WAS를 통해 인증 토큰(JWT / Session)을 검증, 이체 요청을 계정계로 전달
      - 이체 금액이 일정 금액 이상이면 OTP나 생체인증 등 추가 인증 진행
      - FDS 연계
        - 시간대 / 기기 / IP 발생 거래 확인 및 위험도에 따른 거래 보류
      - 입력값 검증
        - 출금 가능 여부 조회 등의 비즈니스 로직 검증은 계정꼐에서 진행
      - 채널계 -> 계정계 or 대외계 (타행 이체 시) 등으로 연결
- 계정계 (코어뱅킹)
  - 원장
    - 법적으로 보관할 의무가 있는 거래의 공식 기록
    - ACID
      - Atomicity (원자성) / Consitency (일관성) / Isolation (격리성) / Duration (지속성)
    - EOD (End of day, 일일 마감)
      - 이자 계산 및 각종 결산 처리 진행
- 정보계
  - 데이터웨어하우스(DW) 구축 및 운영
  - 기처리된 데이터 바탕, 의미 있는 정보 추출
    - KPI 보고서, 고객 세그먼트 분류, 마케팅 활용 CRM, 리스크 관리 및 자금 운용 계획 등
  - 정보계 / 계정계 망 분리
    - 실시간 거래 처리 성능에 영향을 주지 않기 위함
  - 예시
    - ETL (Extract - Transform - Load) 프로세스를 통한 정보계 DW 이관
      - 이후 금감원 제출용 규제 보고서 생성
      - 고객별 신용점수 재산정 및 여신 한도 재계산
      - 마케팅 부서의 고객 세그먼트 분석
  - 실시간성 보다 정확성 및 대용량 처리 최적화
    - RDBMS보다는 컬럼 지향 저장 / OLAP 큐브 등 사용
- 대외계
  - 외부 기관과 데이터 송수신
  - 예시
    - 금결원 타행이체 공동망 / 지로 / CMS(자금관리서비스)
    - 한국은행 BOK-Wire
      - 대금융기관 간 거액 자금 결제
    - 금감원 / 금융위
      - 정기적 감독보고 및 규제 데이터 제출
      - FDS 및 자금세탁방지 데이터 포함

### 웹서비스 구조: Browser -> Web Server -> WAS -> DB
- Browser (클라이언트)
  - 사용자가 가장 먼저 마주하는 화면, 웹 거래의 시작점
  - 기존 ActiveX (플러그인) 사용
    - 브라우저 표준으로 부족한 보안을 보충하기 위해
    - 단점
      - 특정 브라우저에서만 동작
      - 보안 취약점 관리가 어려움
  - 현재 HTML5 기반으로 전환
    - 브라우저 및 운영체제 호환성 확보
  - 모바일
    - 주로 네이티브 앱 사용
      - OS 차원 보안 기능 직접 활용 가능
  - 처리 흐름
    - 버튼 클릭 -> 브라우저는 정적 자원 렌더링 및 클라이언트 단 유효성 검증 -> 요청은 HTTPS(TLS 1.2 이상)로 암호화되어 전송
- Web Server
  - 정적 파일 제공
  - HTTPS 통신 암복호화 담당
    - 주로 443 port 
  - 동적 요청 WAS 바이패스
    - *리버스 프록시*
      - EX) Apache, Nginx 등
      - 보통 클라이언트의 기능을 대체하면 프록시, 서버의 기능을 대체하면 리버스 프록시로 통칭함
  - 처리 흐름
    - 웹 서버 요청 수신 -> 정적 리소스 처리 및 응답 -> 동적 요청 WAS 전달 (리버스 프록시)
    - Web Server는 DMZ에 위치
      - 1차 방화벽 통과한 트래픽만 도달
    - SSL 종단을 처리, 암호화 부담을 분산
      - Web Server 이후에는 Http로 진행
- WAS
  - 비즈니스 로직 실행
  - DB Connection pool
    - DB와의 연결을 미리 만들어두고, 꺼내 쓰고 반납
      - EX) 채널계는 주간 시간대에 짧고 빈번한 조회성 트랜잭션
      - EX) 야간 AP Server 배치는 소수 커넥션으로 대용량 데이터 장시간 처리
      - 주로 배치용 / 온라인용 풀 물리적 분리
        - 동일 풀 공유시, 배치 작업이 커넥션을 오래 점유해 온라인 채널의 응답성을 저해함
  - 세션 관리
    - HTTP는 매번 독립적 요청으로 처리
    - 세션을 통해 로그인 및 거래 진행 상태 유지
  - 트랜잭션 관리
    - 오류 발생 시 롤백
  - 계층별 처리 흐름
    - 셰션/토큰 검증을 통한 사용자 인증
    - 잔액 조회 및 이체한도 검증
    - FDS 연동
    - 트랜잭션 시작
    - 대외계 연동
    - 커밋 or 롤백
  - 주로 2차 방화벽 안쪽 내부망에 위치, 외부에서 직접 접근 불가능
- DB
  - ACID 트랜잭션
  - All or Nothing (Atomicity)
  - 격리수준 Read Committed 이상
    - Non-Repeatable Read / Phantom Read 등은 방지 어려움
